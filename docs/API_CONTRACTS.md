# API contracts

QA additions pending on the linked project: `record_match_open(leg UUID)` requires active campus membership, an open same-campus leg and trip, and returns the trip UUID while incrementing only an aggregate campus/day count. Seat and item-offer acceptance also recheck the counterparty's current campus membership. These behaviors pass locally in PGlite but require the four 2026-10-21 migrations to be applied before they are available in the linked project.

Trips: `createTrip` takes destination, departure (IST), seats 1–8, `acceptsItems` and an optional note; the origin is resolved server-side as the active `IIT Indore Campus` zone. Items: `askToCarry` (trip, leg, description 5–1000, quantity 1–100, budget 0–100000) calls `ask_to_carry`; `answerCarryRequest` (item, fulfilment, accept/decline) calls `answer_carry_request`; `createItem`, `offerItem` and `editItem` were removed. The only auth interface is `signInWithGoogle`, which starts Supabase Google OAuth with `hd=iiti.ac.in` and `prompt=select_account`; `GET /auth/google/callback` exchanges the PKCE code and keeps the session only for a verified `@iiti.ac.in` identity with the Workspace hosted-domain claim. `signOut` ends the session. All community server actions require an active member and validate form input with Zod before calling database RPCs. RPCs derive identity from `auth.uid()` and enforce ownership, campus and state transitions. Implemented functions include `create_own_profile`, `update_own_profile`, `create_trip`, `request_join`, `decide_join`, `withdraw_join`, `set_trip_status`, `create_item_request`, `offer_item`, `accept_item_offer`, `set_item_status`, `open_conversation`, `send_message`, `mark_conversation_read`, `conversation_unread_counts`, `mark_notification_read`, `block_member`, `unblock_member`, `report_content` and `review_report`. A dedicated Supabase test project is linked; key workflows passed fictional-account browser checks, while device and release checks remain. The table below retains planned limits where not yet implemented.

`signInWithGoogle` starts Supabase OAuth with an IIT Indore account-picker hint. `GET /auth/google/callback` exchanges its PKCE code, then requires a confirmed `@iiti.ac.in` email and a verified Google identity with `hd=iiti.ac.in`; it signs out and redirects outsiders to a fixed error state. The linked test project's Google provider must be configured before this flow can run live.

`429` style responses should include a retry interval where applicable. Public error messages must omit email, private message content and undisclosed account status. Exact JSON shapes, field maxima, transport choice and limits are to be finalized with implementation and tests in each phase.

Current database write triggers cap per active member: 10 trips/day, 20 item requests/day, 20 join requests/day, 20 item offers/day, 30 messages/minute, and 10 reports/day. These raise database errors; server actions currently redirect to a generic failure state, so a friendly retry interval remains pending. The limits serialize writes by member using transaction advisory locks. Supabase Auth signup and email limits remain provider configuration.
